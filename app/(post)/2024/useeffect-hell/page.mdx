  description: 'useEffect를 너무 남발했던 코드를 리팩토링하면서 배운 것들.',
}

예전에 짠 코드 보다가 소름 돋았다. `useEffect`가 한 컴포넌트에 8개였다.

```tsx
// 이게 진짜 있었던 코드... 부끄럽다
useEffect(() => { fetchUser() }, [userId])
useEffect(() => { fetchPosts() }, [userId])
useEffect(() => { setTitle(user?.name) }, [user])
useEffect(() => { localStorage.setItem('userId', userId) }, [userId])
useEffect(() => { setIsLoading(true) }, [userId])
useEffect(() => { analytics.track('page_view') }, [])
useEffect(() => { if (error) toast.error(error) }, [error])
useEffect(() => { window.scrollTo(0, 0) }, [pathname])
```

뭔가 잘못됐다는 건 알았는데 어디서부터 손대야 할지 몰라서 방치했었다.


React 공식 문서의 "You Might Not Need an Effect" 읽고 기준이 생겼다.

**useEffect가 필요한 경우:**
- 외부 시스템 동기화 (DOM 조작, 네트워크 요청, 구독 등)
- 컴포넌트 마운트/언마운트 시 실행해야 하는 것

**useEffect가 필요 없는 경우:**
- 렌더링 중 계산 가능한 값 → 그냥 변수로
- 이벤트 핸들러에서 처리 가능한 것 → 이벤트 핸들러로
- 다른 state 변화에 반응하는 state 업데이트 → 대부분 파생 state


위 8개 중 정리하면:

```tsx
// setTitle은 그냥 렌더링 중에 계산
const title = user?.name ?? '로딩 중'

// localStorage는 이벤트 핸들러에서
const handleLogin = (userId) => {
  localStorage.setItem('userId', userId)
  setUserId(userId)
}

// setIsLoading은 fetch 함수 안에서
const fetchUser = async () => {
  setIsLoading(true)
  try {
    const data = await api.getUser(userId)
    setUser(data)
  } finally {
    setIsLoading(false)
  }
}

// analytics는 라우터 이벤트로
// scroll은 Link 컴포넌트나 라우터에서 처리

// 남은 건 이것들만
useEffect(() => { fetchUser() }, [userId])
useEffect(() => { fetchPosts() }, [userId])
useEffect(() => { if (error) toast(error) }, [error])
```


사실 fetch도 useEffect 안에 넣는 게 맞는지 의문이다. 요즘엔 React Query나 SWR 써서 데이터 페칭 로직을 분리하는 게 훨씬 낫다.

useEffect로 fetch 하면:
- 클린업 안 하면 경쟁 조건 생긴다
- 로딩/에러 상태 직접 관리해야 한다
- 캐싱 없다
- strict mode에서 두 번 실행된다 (개발 모드)

TanStack Query 쓰면 다 해결되는 문제들이다. 이걸 왜 이제야 배웠나.
