새 프로젝트 시작할 때마다 상태 관리 라이브러리 선택에서 시간을 날린다.

"Redux 써? Zustand 써? Context API로 해결되나?"

이걸 정리해봤다.

---

**일단 상태를 종류별로 나누는 게 먼저**

상태 관리 라이브러리가 필요한지 여부를 먼저 판단해야 한다.

**서버 상태** (API 데이터): TanStack Query, SWR  
→ 이건 상태 관리 라이브러리가 아니라 데이터 페칭 라이브러리

**전역 UI 상태** (모달 열림/닫힘, 테마, 인증): Zustand, Jotai, Context API  

**폼 상태**: React Hook Form, Formik  

**URL 상태**: useSearchParams, nuqs  

**로컬 컴포넌트 상태**: useState, useReducer

대부분의 "상태 관리" 문제는 TanStack Query 도입하면 해결된다. API 데이터를 useState로 관리하다가 전역으로 공유하려다 보니까 전역 상태 관리 라이브러리까지 끌어오는 패턴이 많다.

---

**진짜 전역 상태가 필요한 경우에는**

**Context API**: 상태가 거의 안 바뀌고 트리 일부에서만 쓰는 경우  
→ 자주 바뀌는 값을 Context에 넣으면 리렌더링 폭발한다

**Zustand**: 심플하고 학습 곡선 낮다, 리렌더링 최적화 괜찮다  
→ 대부분의 경우 이거면 충분하다

**Jotai**: atom 단위 최적화, 필요한 atom 구독하는 컴포넌트만 리렌더링  
→ 상태가 많고 세밀한 최적화 필요할 때

**Redux Toolkit**: 대규모 팀, 디버깅 도구 중요, 미들웨어 필요할 때  
→ 혼자 or 소규모 팀이면 오버킬

---

**Zustand 기본 패턴**

```ts
import { create } from 'zustand'

interface AuthStore {
  user: User | null
  isLoading: boolean
  login: (credentials: Credentials) => Promise<void>
  logout: () => void
}

const useAuthStore = create<AuthStore>((set) => ({
  user: null,
  isLoading: false,
  
  login: async (credentials) => {
    set({ isLoading: true })
    try {
      const user = await authApi.login(credentials)
      set({ user })
    } finally {
      set({ isLoading: false })
    }
  },
  
  logout: () => {
    set({ user: null })
    authApi.logout()
  },
}))
```

---

**리렌더링 최적화**

```tsx
// 전체 스토어 구독 - user, isLoading 둘 중 하나만 바뀌어도 리렌더링
const { user, isLoading } = useAuthStore()

// 필요한 것만 구독 - user만 바뀔 때만 리렌더링
const user = useAuthStore(state => state.user)
const isLoading = useAuthStore(state => state.isLoading)
```

selector 쓰면 불필요한 리렌더링 줄일 수 있다.

---

결론: 프로젝트 시작하면 일단 TanStack Query + Context API로 시작하고, 전역 상태가 복잡해지면 Zustand 추가하는 방식이 제일 무난하다.

Redux는... 정말 필요한 경우가 아니면 안 쓴다.
